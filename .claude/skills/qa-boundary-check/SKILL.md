# 경계면 교차 검증

파일이 있다는 것만으로 통과시키지 않는다. 결함은 대부분 계층 사이에서 생긴다: 컬럼 이름이 바뀌었는데 쿼리가 옛 이름을 쓰거나, API가 `data.items`를 주는데 화면이 `data`를 배열로 읽는 경우.

## 1. 정적 검사 (항상 먼저)
```
node .claude/skills/qa-boundary-check/scripts/static-check.mjs .
```
JS 문법, 비밀값 노출, 화면 `fetch` 경로 ↔ 서버 라우트, 서버 오류 코드 ↔ 화면 처리, 새 테이블 RLS, PUBLIC 권한을 검사한다. `[SYNTAX] [SECRET] [ROUTE] [RLS] [GRANT]`는 결함, `[INFO]`는 판단 자료다. 화면에서 처리하지 않는 오류 코드 목록은 결함이 아닐 수 있으니 계약과 대조해 판단한다.

## 2. 계층 대조
| 대조 | 방법 |
| --- | --- |
| SQL ↔ API | API 쿼리의 테이블·컬럼·스키마 이름이 마이그레이션에 실제로 있는지 Grep. 쓰는 역할에 해당 GRANT와 RLS 정책이 있는지. |
| API ↔ 계약 | 계약의 필드·타입·오류 코드·상태가 코드의 `json(...)`, `error(...)`와 같은지. |
| 계약 ↔ 화면 | 화면이 읽는 `body.data.*` 경로가 계약에 있는지, 계약의 오류 코드가 안내 문구로 매핑됐는지. |
| 정책 ↔ 코드 | `booking-domain-rules`의 불변식 1~9를 해당 코드가 지키는지. |

## 3. 권한 검사
엔드포인트마다 표로 확인: 익명 / 미인증 이메일 / 다른 회원 / 다른 시설 운영자 / 정당한 사용자. 기대 상태 코드와 실제 코드 경로를 적는다. 권한 확인이 쓰기와 같은 트랜잭션 안인지 본다.

## 4. 경합 시나리오 (예약·홀드·결제 코드가 있을 때)
- 같은 자원에 동시 동의 두 건 → 한 건만 결제 대기?
- 동의 직전 새 제안 버전 생성 → 옛 동의 거부?
- 만료 직후 결제 성공 도착 → 확정 안 되고 환불 작업 생성?
- 같은 멱등 키 재요청 → 중복 청구 없음?
- 한쪽만 납부 후 만료 → 납부분 전액 취소 요청?
코드 경로를 따라가며 잠금·재검사·제약 중 무엇이 막는지 근거를 적는다. 막는 장치가 없으면 결함이다.

## 5. 실행 검증 (승인 시에만)
사용자가 허락하면 `npx wrangler dev --config wrangler.development.jsonc` 후 `curl`로 확인한다. 허락이 없으면 "실행 검증: 미실행"으로 적는다.
